# Структурная генерация карт (Картограф)

Документ описывает, как устроен новый движок генерации: зачем он, из каких шагов
состоит, какие инварианты обязан соблюдать и как его расширять.

## Зачем

Раньше решения принимались поклеточно: влажность/высота → террейн, затем независимые
броски «посадить ли дерево в этой клетке». Из-за этого:

- не было композиции (лес, поляна, опушка — однородная каша из деревьев);
- объекты не знали друг о друге (дерево могло стоять в стене, камень — на дороге);
- нельзя было сказать «здесь роща, тропа идёт к ней», «в сокровищнице должен быть сундук»;
- нечем было проверить карту: ошибки сборки просто попадали в результат.

Структурный движок строит карту как **план**: сначала крупные области (zones),
затем точки интереса (POI) и группы объектов, и только потом — расстановка
с проверками занятости и расстояний.

## Пайплайн

1. **Террейн** (без изменений по сути): Perlin fbm для высот и влажности →
   `classify` в террейны; река и дорога сглаживаются (`wavyPath`, `routeRoad`,
   `planRoadNetwork`); постройки — rejection sampling; пещеры — клеточные автоматы;
   склепы — blueprint комнат.
2. **Зоны** (`gen/zones.ts`, `gen/cave.ts`): классификация клеток в зоны
   (dense/medium/sparse forest, clearing, meadow, wetland, rocky, roadside,
   riverbank; для пещер — chamber/tunnel/shore/rubble) с плотностью и границами.
3. **POI** (`gen/forest.ts`, `gen/cave.ts`, `gen/cryptplan.ts`): рощи, поляны,
   лагеря, каменные поля, залы, водоёмы, вход в пещеру, назначения залов склепа.
4. **Группы** (`ObjectGroup`): роща ставит 3+ дерева, лагерь — кольцо камней и
   сушняка, склеп — ряды гробов, алтари, охрану, тайники.
5. **Размещение** (`gen/occupancy.ts`): `OccupancyGrid` (FREE / SOFT / BLOCKED) и
   `SpatialHash` — проверка клетки, габаритов и минимальной дистанции.
   Джиттер координат ограничен `clampToCell`, чтобы округление стойки не уезжало
   в соседнюю (возможно, стену).
6. **Тропы и дороги** (`gen/roads.ts`, `gen/forest.ts`): магистраль Дейкстрой по
   стоимости террейнов, обочины `carveVerges`, тропы к POI (Дейкстра со
   диагоналями и запретом срезать углы), мосты по воде.
7. **Обстановка** (`gen/cryptplan.ts`): `furnishByPurpose` — сокровищница без
   сундука его получает, крипта — скрытый тайник, стража — ловушку; в коридорах —
   скрытые ловушки.
8. **Починка** (`gen/repair.ts`): деревья/камни вне земли, двери в стене,
   предметы на двери, осиротевшие клетки дороги, залы, отрезанные от входа
   (прорубается проход). Каждое действие записывается в `plan.actions`.
9. **Валидация** (`gen/validate.ts`): проблемы (связность пола ≥ 97 % для
   пещер/склепов, объекты на запрещённом террейне, дверь без прохода, пустой зал,
   отсутствие входа) и предупреждения (POI без подхода, старт на непроходимом).
   Результат — `plan.report`.
10. **Рендер** (`render.ts`): материалы и спрайты с вариантами, декор по зонам,
    сглаженные ленты реки, настилы мостов, силуэт воды, debug-разметка.

## Контракт данных

`MapData.plan?: GenerationPlan` (поле optional — старые проекты читаются).

```
GenerationPlan {
  version: 1
  engine: 'structured'
  zones: Zone[]
  poi: Poi[]
  groups: ObjectGroup[]
  roads?: RoadPath[]        // id, type: main|trail, width, points, bridges, surface
  roadGraph?: RoadGraphEdge[]
  rooms?: DungeonRoom[]     // id, purpose, bounds, depth
  graph?: { from, to, length }[]
  spawn?: Point             // стартовая зона партии
  report?: MapReport        // ok, problems, warnings, stats
  actions?: string[]        // что починили
}
```

Все точки — координаты клеток (float для объектов, integer для POI/залов).

## Инварианты

- **Детерминизм**: только `SeededRandom` (mulberry32). Никаких `Math.random`,
  `Date.now`, обхода объектов без сортировки. Тест проверяет побайтовое совпадение
  результатов при одном сиде и различие при разных.
- **Обратная совместимость**: `generationEngine: 'structured' | 'legacy'`
  (по умолчанию `structured`, тумблер «Структурная генерация (эксперимент)» в
  панели генерации). `layout-test` фиксирует, что загрузка/сериализация проектов
  не меняется.
- **Починка не переделывает замысел**: исправляется только то, что нарушает
  правила (объект не на земле, зал отрезан), остальное не двигается.
- **Проверяемость**: у каждой карты есть `report`; тесты требуют `report.ok`
  для 8 биомов.

## Морфология террейна (`src/lib/gen/morphology.ts`)

После нормализации карта проходит два-три прохода морфологии — это убирает
«лего» из одноклеточных вкраплений и рваных кромок:

- `despeckle` — клетка грунта, у которой среди 8 соседей нет ни одной такой же,
  растворяется (в большинстве соседей, иначе в базовый грунт биома; если вокруг
  вода — затапливается);
- `softenWaterEdges` — одиночный выступ воды (≤2 водных соседа) заливается
  грунтом, одиночный островок суши в воде (7+ водных соседей) — топится;
- `smoothGround` — на стыке травы и тёмной травы клетка с 6+ соседями другого
  оттенка перекрашивается, поэтому граница читается волной, а не ступенькой.

Защищённые террейны (дорога, мост, стена, пол, дверь, вода, void) не меняются —
это проверяется тестом «сглаживание не трогает дороги, мосты и постройки».
Морфология детерминирована: обход фиксированный, «ничьи» решаются большинством.

## Как расширять

- **Новый биом**: `Biome` в `types.ts`, `BIOME_PLAN` в `gen/catalog.ts`
  (плотности по зонам + допустимые POI), `treeKinds` в `generator.ts`,
  цвета в `palette.ts`.
- **Новый объект**: файл спрайта `src/assets/cartography/<id>.webp` (варианты —
  `<id>-2.webp`), запись в `SPRITE_CATALOG` (biomes, preferredTerrain,
  footprint, minDistance).
- **Новая зона**: `ZoneType` в `gen/plan.ts`, правила в `gen/zones.ts`,
  цвет/подпись в `DEBUG_ZONE_FILL` для debug-разметки.
- **Новое правило размещения**: проверка в `OccupancyGrid.canPlace` или
  дополнительный проход после `plant` (как `roadClearance`, `treeNearby`).

## Производительность

Замеры генерации (Node, без рендера): 44×30 forest — 33 мс, 60×45 town — 32 мс,
48×32 dungeon — 27 мс, 60×45 cave — 27 мс, 100×80 forest — 93 мс.
Рендер ограничен бюджетом пикселей (`renderPixelRatio`, 16 Mpx), поэтому плотные
большие карты не раздувают память.


## Композиционный слой (MapComposition)

Помимо плана (`GenerationPlan`) карта несёт композицию — порядок «сначала
пространство, потом объекты»:

```
пространства (OpenSpace) → массы (MassRegion) → переходы (TransitionZone)
→ тактика (TacticalSpace) → зоны → POI → композиции → группы → объекты → декор
```

- `src/lib/gen/composition.ts`: `buildComposition()` строит композицию по террейну,
  дороге, реке и полю зон: главный визуальный центр (площадка боя с проверкой
  доли открытого грунта), площадка у дороги, заводь у реки, 2–4 массы леса,
  переходные полосы вокруг пространств и тактические зоны (`open_area`,
  `cover_area`, `transition`, `ambush_area`, `crossing`).
- Плотность растительности берётся из `compositionDensity()`: в открытых
  пространствах строго 0, в массе — плавный градиент (`influence^1.45`), в
  переходной кайме — средний уровень.
- Резерв: все `OpenSpace` помечаются в `OccupancyGrid` как заблокированные, поэтому
  ни дерево, ни камень туда не попадут; валидатор дополнительно проверяет
  «открытое пространство заставлено объектами».
- Объект, который не объясняется композицией (вне масс, вне переходов), ставится
  с малой вероятностью — карта не превращается в равномерный шум.

## Композиция пещер и поселений

Композиционный слой (`src/lib/gen/composition.ts`) общий для всех биомов; для
подземелий и городов есть отдельные сборщики:

- `buildCaveComposition({ width, height, cells, chambers, pools, entrance })` —
  крупнейший зал становится ареной боя (`battle_area`, id `battle_cave`),
  остальные залы — `clearing`, водоёмы — `landmark`, вход — `landmark` с
  тактикой `chokepoint`. Сталагмитовые поля (`masses`, kind `rocky`) ставятся
  на кромке залов, переходные зоны — `cave_edge` (открытый зал → каменные
  стены).
- `buildSettlementComposition({ width, height, cells, plaza, buildings })` —
  площадь (клетки `plaza`) становится `battle_area`, вокруг каждого дома —
  `yard` радиусом `max(2.4, max(w, h) / 2 + 1)`, переход — `town_edge`
  (дворы → улицы → кварталы).
- Декор уважает открытые пространства: в пещере грибы/сталагмиты уходят на
  кромку через `clearRadius()` (не ближе `0.76 * space.radius`), в поселении
  `plant`/`dropRock` отказываются от клеток внутри `insideOpenSpace(..., 0.2)`.
- Валидатор `validateMap` проверяет все открытые пространства (`battle_area`,
  `clearing`, `yard`): препятствие внутри `0.7 * radius` даёт проблему
  `open_space_blocked`. Это общий контракт «арена должна быть пригодна для боя».

## Сцена (`src/lib/gen/scene.ts`) — MACRO-слой замысла

До генерации террейна строится `ScenePlan`: архетип сцены, река (если уместна),
дорога, точка переправы, открытые пространства, массы леса, важность элементов
и бюджет композиции (`DEFAULT_BUDGET`).

Порядок внутри `planScene`:
1. решение «нужна ли река» (биом + настройки + шанс);
2. точка переправы выбирается ДО реки и дороги — переправа является центром сцены;
3. река строится как безье-кривая между ПРОТИВОПОЛОЖНЫМИ краями (делит карту на
   два берега) с меандром, покрытие держится в 8–14 % площади;
4. дорога идёт с берега на берег через переправу (waypoint) с изгибом подходов;
5. главное открытое пространство (`battle`) ставится ПОПЕРЁК русла рядом с
   переправой; вторичная поляна, лагерь и массивы леса — по бюджету;
6. бюджет и иерархия важности (`primary/secondary/tertiary/decorative`)
   ограничивают число крупных элементов.

`GenerationPlan.scene` сохраняет сцену; `roads.ts` принимает
`RoadPlannerOptions { entry, exit, waypoints }` и прокладывает тракт сегментами
`entry → via[] → exit`, а мост проектируется по реальному пересечению с водой
(`plan.bridges`).

## CompositionValidator (`src/lib/gen/composition-validate.ts`)

Базовый `validateMap` отвечает на вопрос «можно ли играть»; композиционный
валидатор отвечает на вопрос «получилась ли сцена». Пять категорий:

- `structure` — есть ли `battle_area`, пригодно ли ядро пространства для боя
  (проходимо ≥ 55 % клеток в радиусе `0.6 * radius`), не слиплись ли пространства;
- `road` — связна ли дорога (8-связность, т.к. полотно шириной 2 может идти
  «через угол»), нет ли тупиков в пустоте (кроме краёв карты и площадок);
- `river` — покрытие 6–24 % при наличии реки, не больше трёх водоёмов,
  обязательная переправа, если есть и река, и дорога;
- `forest` — нет ли крон в боевой поляне, читается ли лес группами
  (медиана расстояния до соседа ≤ 3.2 кл., одиночек ≤ 25 %);
- `gameplay` — достижимы ли все открытые пространства от точки старта,
  не отрезана ли от старта большая часть дороги.

Функции: `validateCompositionMap(map)` и `validateCompositionAcross(maps)`.
Тест `scripts/structured-gen-test.ts` прогоняет 20 сидов лесного пресета
44×30 и требует отсутствия блокирующих проблем.

## Руины как сцена, водоёмы с причиной, локальный ремонт

- **Руины.** Двор (`yard`) вокруг постройки/руины получает: расчищенный центр
  (без растительности), обломки кладки по кольцу (5–8 мелких камней), заросли
  кустов/грибов по внешнему краю (`radius + 1.0..2.3`) с открытым сектором со
  стороны подхода и тропу от двора к дороге. Открытый сектор считается от
  направления тропы (`atan2(start.y - yard.y, start.x - yard.x)`), поэтому
  подход всегда читается как «вход», а заросли как «стена».
- **Водоёмы только с причиной.** Нормализация оставляет воду, если это крупный
  водоём, если над ним проектируется переправа, или если это родник/пруд у
  массива леса либо у ориентира (`landmark`) из композиции (`reasonedWater`).
  Остальные лужи расходятся в грунт (`муд` в болоте).
- **Локальный ремонт (`repair.ts`).** Помимо объектов «вне земли», ремонт
  вычищает деревья и камни из ядра открытых пространств (`battle_area`,
  `clearing`, `yard`, радиус `0.7 * radius`) и осушает центр боевой поляны,
  если он оказался в воде (грунт по биому). Это точечные правки: ремонт не
  перестраивает карту и не меняет замысел сцены.

## Рендер воды и переправ

- Берег и песчаный пояс рисуются **только вне воды**: путь клипа = холст минус
  клетки воды (`ctx.clip('evenodd')`). Поэтому растушёванный песок не наползает
  на поверхность реки и внутри воды не появляется земляное кольцо.
- Клетки воды заливаются скруглёнными блобами чуть шире клетки, поверх —
  гладкая лента по осевой линии; это закрывает стык у берега.
- На одну переправу — **один настил**: `dedupeBridges` в `gen/roads.ts`
  оставляет самый длинный мост, отбрасывая наложенные (в пределах 2.5 клеток),
  так как магистраль и ответвление могут пересекать одну протоку рядом.
  Настил шире полотна на 0.4 клетки и длиннее водного пробега на 2.2 клетки,
  поэтому он накрывает клеточные «обрезки» настила и читается цельной доской.

## Рынок (`src/lib/gen/marketArchetypes.ts`, `src/lib/gen/marketLayout.ts`)

Рынок — часть планировки поселения, а не отдельный генератор. Архетип (назначение и состав) и `marketStyle` (геометрия рядов) независимы.

1. **Место** — `resolveMarketSite`: ровные сухие клетки, взвешенные по близости к центру и дорогам, свободному месту и воде (для порта — берег). Если подходящего места нет, архетип заменяется по цепочке `fallback`.
2. **Границы и входы** — рамка по `size` архетипа. Входы ставятся только там, где к рамке подходит улица; близкие входы сливаются.
3. **Проходы** — до мест: главный, боковые, поперечные, подходы от входов, служебный двор. Коды — `LANE`.
4. **Зоны и места** — свободные клетки вдоль проходов режутся на «прогоны»; каждое место — шаблон «прилавок + навес + запас + тара» лицом к проходу. Затем `backfill` отдаёт месту ряд клеток за его спиной под запас.
5. **Насыщенность** — у каждого предмета есть порог; скелет имеет порог 0. Поэтому набор при 0.3 — подмножество набора при 0.9.
6. **Покраска** — `applyMarketGround`: проходы `road`, места — `dirt`/`grass`, `plaza` только при покрытии 'square'; мокрые клетки не трогаются.
7. **Проверка** — `validateMarket`: границы, наложения, центр, проходы, доступ, входы, товары у своих мест, состав, декор, размер, телеги.
